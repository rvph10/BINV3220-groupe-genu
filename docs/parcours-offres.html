Parcours de la liste des offres

De la page React à SQLite, puis retour des données vers le tableau. Ce document décrit le code existant ; le filtre par période présenté à la fin est une proposition, pas une fonctionnalité déjà disponible.

App → page → hook → service frontend → API Express → contrôleur → service → repository → SQLite

Vue d’ensemble

frontend/ contient l’interface React : les pages assemblent des composants, les hooks gèrent les états et les services appellent l’API. backend/ contient l’API Express : les contrôleurs traitent les requêtes, les services appliquent les règles métier et les repositories interrogent SQLite.

En développement, Vite transmet les appels /api/… au backend en retirant /api : voir frontend/vite.config.ts. Le schéma de la base se trouve dans 001_initial.sql.

1. De React à la requête HTTP

  1. Route de l’interface. Dans frontend/src/App.tsx, App ouvre la route /offres pour un utilisateur connecté autorisé par canListOffers. Il transmet à OffersPage l’utilisateur, le jeton et auth.logout comme gestionnaire de session expirée.
  2. Page. OffersPage, dans OffersPage.tsx, appelle useOffers(token, onUnauthorized). Selon le résultat, elle affiche le chargement, l’erreur, l’état vide ou le nombre d’offres et OfferTable.
  3. Hook. useOffers, dans useOffers.ts, lance getOffers dans un effet, conserve les offres et les états de chargement et d’erreur, et annule la requête avec AbortController au nettoyage. Une réponse 401 déclenche onUnauthorized.
  4. Service frontend. getOffers, dans frontend/src/services/offers.service.ts, envoie GET /api/offers avec le jeton brut dans Authorization. readJson, dans api.ts, vérifie le statut et le JSON avec isOfferList de guards.ts.

2. De la route API à SQLite

  1. Montage et authentification. createApp dans backend/src/app.ts construit les repositories et services, puis monte createOffersRouter sur /offers après le middleware authenticate. Celui-ci vérifie le jeton et recharge l’utilisateur : voir authenticate.ts.
  2. Contrôleur. createOffersRouter dans offers.controller.ts traite GET /offers. authorize(canListOffers) vérifie les droits ; le gestionnaire appelle listOffers(getCurrentUser(req)), applique toOfferDto et renvoie le tableau JSON. Les règles sont définies dans permissions.ts.
  3. Service métier. createOffersService et sa méthode listOffers, dans backend/src/services/offers.service.ts, appellent visibilityFilter puis repository.findAll et convertissent les lignes avec toOffer. L’administrateur voit toutes les offres ; l’étudiant uniquement les offres publiées ; le contact déposant uniquement ses propres offres. Un contact sans rôle de déposant est refusé avec 403.
  4. Repository et requête. createOffersRepository et sa méthode findAll, dans offers.repository.ts, exécutent une requête préparée. Les filtres de visibilité sont liés comme paramètres ; une valeur null désactive le filtre correspondant.
SELECT o.id, o.title, o.description, o.status,
       o.company_id, c.short_name AS company_short_name,
       o.depositor_contact_id,
       ay.label AS academic_year_label, p.code AS period_code,
       o.created_at, o.updated_at
FROM offers o
JOIN companies c ON c.id = o.company_id
JOIN academic_years ay ON ay.id = o.academic_year_id
JOIN periods p ON p.id = o.period_id
WHERE (@status IS NULL OR o.status = @status)
  AND (@depositorContactId IS NULL OR o.depositor_contact_id = @depositorContactId)
ORDER BY ay.start_date DESC, o.created_at DESC

La jointure avec periods fournit déjà le code de période. Les offres sont triées par année académique décroissante, puis par date de création décroissante.

3. Retour des données et affichage

Dans offer.mapper.ts, toOffer convertit chaque ligne OfferDbo en objet métier, puis toOfferDto construit la réponse publique. Le frontend valide ce tableau, le hook met son état à jour et OffersPage transmet les offres à OfferTable, dans OfferTable.tsx. Le tableau traduit les codes de période avec PERIOD_LABELS dans labels.ts.

Ajouter un filtre par période

Une approche possible consiste à ajouter un paramètre facultatif period à GET /offers, filtré par le serveur. L’absence de paramètre signifie « toutes les périodes » ; les valeurs transmises sont P1, P2 et OTHER (« Autre »). Le filtre doit s’ajouter aux restrictions de visibilité, jamais les remplacer.

  • OffersPage.tsx : ajouter un sélecteur accessible et son état, avec une option « Toutes » ; transmettre la sélection au hook.
  • frontend/src/models/offer.ts et labels.ts : réutiliser PeriodCode, PERIOD_CODES et PERIOD_LABELS, déjà définis. Le format de l’offre retournée ne change pas.
  • useOffers.ts : accepter la période, relancer et annuler le chargement lorsqu’elle change, et gérer correctement les états de chargement et d’erreur.
  • frontend/src/services/offers.service.ts : transmettre la période facultative dans la chaîne de requête, par exemple avec URLSearchParams.
  • offers.controller.ts : lire et valider le paramètre facultatif, refuser les valeurs inconnues ou répétées avec une erreur 400, puis le transmettre au service.
  • backend/src/services/offers.service.ts : combiner la période demandée avec visibilityFilter(viewer) avant d’appeler le repository.
  • offers.repository.ts : étendre OfferFilter, les paramètres et la requête préparée avec un filtre facultatif sur p.code, combiné par AND aux filtres existants. Le type PeriodCode existe déjà dans backend/src/models/offer.ts. Le schéma stocke déjà les trois codes : aucune migration n’est nécessaire pour cette approche.
  • backend/tests/offers.test.ts et frontend/tests/OffersPage.test.tsx : couvrir les choix de période, l’absence de filtre, les entrées invalides et le maintien des restrictions selon les profils.
  • backend/API.md et backend/http/offers.http : documenter le paramètre et ajouter des exemples de requêtes.

Une alternative serait de filtrer uniquement en mémoire côté interface, puisque chaque offre reçue contient déjà period. Dans ce cas, seules les couches frontend et leurs tests changent ; le serveur continuerait toutefois à envoyer toutes les offres visibles.

Commandes de vérification

À la racine du dépôt, après installation des dépendances avec npm ci :

  • npm run lint : Oxlint sur les deux espaces de travail.
  • npm run typecheck : vérification TypeScript.
  • npm test : tous les tests Vitest.
  • npm run build : compilation du backend et du frontend.
  • npm run check : enchaîne lint, typecheck, tests et build.
  • npm test --workspace=backend -- tests/offers.test.ts : tests API des offres ; npm test --workspace=frontend -- tests/OffersPage.test.tsx : tests de la page.
  • Ajouter -t "nom du test" après le fichier pour cibler un test par son nom.

Pour lancer l’application localement : npm run setup une première fois, puis npm run dev. Voir le README et architecture.md pour davantage de contexte.
